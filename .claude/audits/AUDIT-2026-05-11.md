# Auth Server — Deep Audit (April 2026)

Scope: `/home/rw3iss/Sites/ven/new/auth/auth-server/` at HEAD.
Goal: assess fitness as a company-wide centralized authentication backend (multi-tenant, multi-app, RBAC, mixed registration flows, frontend-SDK ready).

This audit focuses on **unknown** gaps. The following items from `CLAUDE.md` "Roadmap" are already known and are not re-listed as findings: per-org SSO, TOTP 2FA, async email, custom per-org roles, dual-secret rotation, webhooks, IP whitelisting, impersonation, hard-delete, audit log writer.

Severity legend: **Critical** = active security risk or data leak. **High** = production blocker / wrong default. **Medium** = important improvement. **Low** = nice-to-have.

## 1. Security review

### 1.1 Password reset tokens are not single-use — reusable until expiry  *(Critical)*

`internal/service/auth_service.go:678-713` (`ResetPassword`) validates the JWT, hashes the new password, updates the user, and revokes refresh tokens — but **never calls `MarkPasswordResetTokenUsed`** or otherwise consumes the stored `password_reset_tokens` row. The infrastructure exists (`internal/repository/postgres/token_repository.go:218`), and the JWT carries the `jti` of the stored row (`internal/auth/jwt/service.go:378`), but the service never looks the row up. Combined with the JWT being self-contained for an hour (`AUTH_PASSWORD_RESET_EXPIRY=1h`), this means:

- A reset link, if leaked from an inbox, an HTTP referrer, or a compromised log, can reset the password **as many times as the attacker likes** within an hour.
- `InvalidateUserPasswordResetTokens` is called at issue time but the row itself is never marked `used` after consumption.

**Fix:** in `ResetPassword`, after `ValidatePasswordResetToken` succeeds, look up the stored row by `claims.ID` (the JWT `jti` is the `password_reset_tokens.id`), reject if `used=true`, then call `MarkPasswordResetTokenUsed(ctx, id)` inside the same transaction as the password update. Also load by ID rather than by hash so the JWT's `jti` is the only handle.

### 1.2 Email verification tokens are not single-use either  *(High)*

`internal/service/auth_service.go:716-733` (`VerifyEmail`) — same shape as 1.1. The row is created at issue time but `MarkEmailVerificationTokenUsed` is never called. Lower impact than password reset (the worst case is "user verifies their own email twice"), but it's still wrong: if a verify link is reused after a malicious actor changed the user's email, the legitimate user can be tricked into re-verifying an attacker-controlled email.

**Fix:** mirror 1.1's pattern. Look up by `claims.ID`, reject if `used=true`, mark used after success.

### 1.3 Bcrypt cost from config is silently ignored  *(High)*

`internal/config/config.go:237` exposes `BCRYPT_COST` (default 12), but `pkg/shared/utils/utils.go:19` calls `bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)` — `bcrypt.DefaultCost` is **10**, not 12. Operators who increase `BCRYPT_COST` for production will get no behavioral change, and the CLAUDE.md claim of "cost 12" is false.

**Fix:** thread `cfg.Security.BcryptCost` into a stateful `Hasher` (or pass cost into `HashPassword`). Validate cost ≥ 10 and ≤ 14 at boot.

### 1.4 No max password length — bcrypt input DoS surface  *(High)*

`internal/service/auth_service.go:97` only enforces `PasswordMinLength`. Bcrypt accepts arbitrary input but truncates internally to 72 bytes; passing a multi-MB password on every login wastes CPU before the truncation. Combined with 1.3 (cost=10), an attacker can flood `/auth/login` and `/auth/register` and burn cycles.

**Fix:** reject passwords longer than 128 chars in `ValidatePassword` (`pkg/shared/utils/utils.go:134`). Apply at login *and* registration. This is a common, low-cost defense.

### 1.5 Password validator is partially broken  *(High)*

`pkg/shared/utils/utils.go:149`:

```go
result.Errors = append(result.Errors, "Password must be at least "+string(rune(minLength+'0'))+" characters")
```

`string(rune(8+'0'))` produces the character `'8'` for minLength=8 — accidentally correct for minLength<10, but for any operator who sets `AUTH_PASSWORD_MIN_LENGTH=12` the message becomes garbage (`<` for 12). Not a security issue per se, but it **leaks the bug into the error response** the user sees, and the single-character error confuses users into entering 1-character passwords.

Also at `utils.go:208-215`: the validator hard-requires both upper+lower and at least one digit, even though `AUTH_PASSWORD_REQUIRE_SPECIAL` is configurable and there's no toggle for "require uppercase" / "require digit". Operators have no way to relax these rules without code changes.

**Fix:** use `fmt.Sprintf("%d", minLength)`. Make each character class requirement (`require_upper`, `require_lower`, `require_digit`, `require_special`) configurable. Document the policy in `CLAUDE.md`'s gotchas.

### 1.6 JWT `aud` and `iss` claims are not validated  *(High)*

`internal/auth/jwt/service.go:225-237` calls `jwt.ParseWithClaims` with only a key callback. `golang-jwt/jwt/v5` validates `exp`/`nbf` automatically, but **does not validate `aud` or `iss` unless you configure parser options**. A token issued by a different system with the same secret would pass. Even more concerning: password-reset and email-verification tokens are signed with `s.cfg.AccessTokenSecret` (`service.go:384, 454`), and they validate the same way (`service.go:389, 459`). So a leaked password-reset token could be presented to `/auth/me` if the same secret is shared and the type discriminator weren't checked — fortunately `service.go:244` does check `claims.TokenType != types.TokenTypeAccess`, but the password-reset/email-verify claim types don't carry that field.

**Fix:** construct the parser with `jwt.WithAudience(cfg.Audience...)`, `jwt.WithIssuer(cfg.Issuer)`, `jwt.WithLeeway(30*time.Second)`. Add a `token_type` claim to `PasswordResetClaims` and `EmailVerificationClaims` and check it on validation. Issue password-reset/email-verify tokens with **distinct secrets** (or a derived secret using HKDF over `AccessTokenSecret + purpose`) — see fix in 1.7.

### 1.7 Password-reset and email-verification tokens reuse `AccessTokenSecret`  *(High)*

`internal/auth/jwt/service.go:384` (reset) and `:454` (verify) sign with `s.cfg.AccessTokenSecret`. If that secret is rotated to invalidate access tokens (e.g. after a breach), every outstanding password-reset link silently breaks. Conversely, if a reset secret needed to be rotated separately, you can't.

**Fix:** add `JWT_RESET_SECRET` and `JWT_VERIFY_SECRET` env vars (or HKDF-derive from a master secret with purpose strings like `"reset"` / `"verify"`). At minimum, add a `purpose` claim and reject if the parsed `purpose` doesn't match the validation context.

### 1.8 JWT secret strength is not validated at boot  *(High)*

`internal/config/config.go:252-260` only checks that `AccessTokenSecret` and `RefreshTokenSecret` are non-empty. The `CLAUDE.md` says "32+ chars, shared with auction/api" but that's not enforced. An operator who sets `JWT_ACCESS_SECRET=test` ships to production unprotected.

**Fix:** in `Validate()`, require length ≥ 32. Reject if `AccessTokenSecret == RefreshTokenSecret`. In production mode, also reject obviously-weak values (entropy heuristic or a hardcoded denylist of `secret`, `changeme`, `test`, etc.).

### 1.9 Refresh token theft is detected weakly — no family revocation on reuse  *(High)*

`internal/auth/jwt/service.go:316-331` (`RefreshTokens`):
1. Validate the refresh JWT.
2. Revoke the old token row.
3. Issue a new pair.

If an attacker steals refresh token T1 and uses it before the legitimate user does, the attacker rotates to T2 and the user's next refresh of T1 will now fail (T1 is revoked). That's correct in shape. But:
- **The user's still-valid access token lives for 15 minutes**, and there's no signal back to the user that anything happened.
- There's no concept of a refresh-token *family* (a chain of rotations from one initial issuance). The standard recommendation is: when a **revoked** refresh token is presented again — i.e., reuse detected — revoke every descendant of the family, not just that one row.

Today, presenting a revoked T1 returns `errors.TokenRevoked()` (`service.go:303`), but the family rooted at T1 (T2, T3, …) keeps working for the attacker.

**Fix:** add a `family_id UUID` and `parent_id UUID` to `refresh_tokens`. On `RefreshTokens`, if the presented token is **revoked but valid-looking**, call `RevokeAllInFamily(family_id)` and emit a security event. This is a small schema change and a well-understood OAuth pattern (RFC 6819 §5.2.2.3).

### 1.10 Logout-all does not blacklist outstanding access tokens  *(High)*

`internal/auth/jwt/service.go:341-347` (`RevokeAllUserTokens`) terminates sessions and revokes refresh-token rows. It does **not** add `auth:blacklist:{jti}` entries for the user's outstanding access tokens. So a user (or admin, via `POST /admin/users/{userId}/revoke-sessions`) "logs out everywhere" but a stolen access token continues to work for up to `JWT_ACCESS_EXPIRY=15m`.

`RevokeRefreshToken` at `service.go:336` blacklists the **refresh** token's `jti` for `AccessTokenExpiry`, which is the wrong key — downstream services check the access token's `jti`, not the refresh token's.

**Fix:** when issuing tokens, store every outstanding access-token `jti` in a per-user Redis set (`auth:user_jtis:{user_id}`). On revoke-all, fetch the set and SET each as `auth:blacklist:{jti}` with TTL = remaining access lifetime. Alternatively, increment a per-user "token version" counter on logout-all and check it during validation. The version-counter approach is cheaper.

### 1.11 Access token cache bypasses signature re-validation, so revocation is racy  *(Medium)*

`internal/auth/jwt/service.go:194-223`: if a token is in the cache, it returns the cached claims **without re-checking the blacklist** — the blacklist check happens *before* the cache hit at line 190, but only on the raw bearer token's hash. Since the cache is keyed by token hash and the blacklist is keyed by `jti`, the two paths can disagree. More importantly, the cached entry has its own TTL = remaining token lifetime, so a token blacklisted *after* it's cached for the first time will continue to validate from cache until natural expiry on this replica.

Worse, the cache is a **per-token-hash JSON blob**, not a `jti` reference. Two replicas can have slightly different caches.

**Fix:** drop the validated-token cache. JWT signature validation is fast (microseconds) and sharing a cache for it is premature optimization. Or, if kept, key the cache by `jti` and check the blacklist on every cache hit, not before.

### 1.12 SSO state is per-replica in-memory  *(High)*

`internal/auth/sso/manager.go:42-101` — `InMemoryStateStore` is the only implementation, and `cmd/server/main.go:58` constructs the manager with `nil` so the in-memory store is always used. `routes.go` does not even know about SSO state. In a multi-replica deployment behind a load balancer, this means the user is sticky-routed to the replica that minted the state — or the callback fails. SSL termination + LB hashing rules are operator-configured; a single misconfiguration silently breaks SSO.

**Fix:** add a `RedisStateStore` (5-minute TTL, GETDEL on validate). Wire it in `main.go` when Redis is connected. Fall back to in-memory only when Redis is genuinely unavailable, and log a loud warning.

### 1.13 SSO redirect URL is not validated against an allowlist  *(High)*

`internal/api/handlers/auth_handler.go:284-302` (`GetSSOAuthURL`) accepts an arbitrary `redirect_url` from the client and embeds it into the OAuth flow. The same `redirect_url` is later used by the provider to redirect the user back. Without an allowlist, an attacker can craft `POST /auth/sso/url { redirect_url: "https://evil.com/..." }`, get a valid Google auth URL pointing back to evil.com, and harvest the `code+state` (which they then submit to `/auth/sso/callback` to log in as the victim — though state is one-shot, the attack works *once per state*).

This is the textbook OAuth open-redirect / authorization-code-injection vulnerability.

**Fix:** add `SSO_ALLOWED_REDIRECT_URLS` env (comma-separated) and reject `redirect_url`s not in the list. Each SSO provider's configured `RedirectURL` (`config.go:188-196`) should be the only accepted value, with optional path-suffix wildcards. Note the test for redirect-allowlist must be the actual host/scheme, not just `strings.HasPrefix`.

### 1.14 SSO callback double-submission is a TOCTOU race on user creation  *(Medium)*

`internal/service/auth_service.go:421-465`: `SSOLogin` does `GetByProviderID` → fall back to `GetByEmail` → fall back to `Create`. If two requests with the same code+state arrive (state is one-shot, so this requires hitting the same state validation roughly simultaneously, but React strict-mode and retries make it possible), both can pass the state check (the deletion at `manager.go:235` is between Get and Delete — not atomic), reach `Create`, and one fails on the unique constraint.

The state store at `manager.go:73-88` reads under RLock then deletes under WLock — between these calls another goroutine can read the same state.

**Fix:** make state validation atomic. For Redis, use `EVAL` with a Lua script that does GET-and-DEL atomically (or `GETDEL` in Redis 6.2+). For the in-memory fallback, use a single mutex around the whole get+delete. Then in `SSOLogin`, wrap the upsert in a transaction with explicit conflict handling.

### 1.15 Rate limiter trusts X-Forwarded-For without proxy verification  *(High)*

`internal/api/middleware/middleware.go:208-231` (`getClientIP`) takes the first comma-separated value of `X-Forwarded-For` *unconditionally*. If the auth server is exposed directly (not behind a verified proxy) or if the proxy doesn't strip incoming XFF, **any client can spoof its source IP** by sending `X-Forwarded-For: 1.2.3.4` and bypass the per-IP rate limit (or get someone else rate-limited).

This is also true for IP-logging in refresh-token rows and sessions.

**Fix:** add `TRUSTED_PROXIES` env (CIDRs). Only accept XFF from listed proxies; otherwise use `RemoteAddr`. Take the **last** XFF entry that matches a trusted CIDR, not the first. Document that operators must configure their proxy to strip incoming XFF.

### 1.16 Rate limiter is per-replica in-memory when Redis is unavailable  *(Medium — known, partly)*

CLAUDE.md mentions this. What's not noted: `middleware.go:147-192` falls through from Redis to in-memory **on Redis error** (line 164 "Fall through to in-memory on Redis error"). On a hot Redis flap or connection-pool exhaustion, every replica silently becomes unprotected. There's no metric or alarm.

**Fix:** in production mode, fail closed (return 503) on Redis error rather than falling through. Or add `RATE_LIMIT_FAIL_OPEN=false` to make this configurable. Either way, emit a metric.

### 1.17 No per-account login rate limit / lockout extension  *(Medium)*

The lockout (`auth_service.go:303`) kicks in after 5 failed attempts in the lifetime of `LockoutDuration` (15m). But the rate limiter is per-IP. An attacker with a botnet (one attempt per IP) can iterate through every popular password against a known-good email indefinitely. No account-level rate limit exists.

**Fix:** add a per-email lockout tracker in Redis (`auth:login_attempts:{email_hash}`) with a sliding window. Lock or CAPTCHA-challenge when exceeded, regardless of source IP.

### 1.18 Bearer extraction also accepts `?access_token=` query and `access_token` cookie  *(Medium)*

`internal/api/middleware/auth.go:227-248`: `extractToken` accepts the token from query string (logged in access logs everywhere) and cookies (no SameSite/Secure/HttpOnly enforcement on issuance because the server doesn't issue cookies). The query-param path is dangerous: tokens leak into browser history, server access logs, referrers, and analytics.

**Fix:** delete the query-string fallback. Keep cookie support only when the server actually issues HttpOnly cookies. For the planned browser SDK, see §9.

### 1.19 CORS supports `*` with credentials  *(High)*

`internal/api/middleware/middleware.go:40` permits `*` as an allowed origin. When any allowed origin matches, line 47 echoes `Access-Control-Allow-Origin: <origin>` and line 50 sets `Access-Control-Allow-Credentials: true`. Browsers reject the combination `*` + credentials, but this code never actually sends `*` — it echoes the origin — so the **browser-side guard is bypassed**: any origin gets credentials access if `CORS_ORIGINS=*`.

The default in `config.go:148` is `*`. Anyone deploying with the default is vulnerable.

**Fix:** if `CORS_ORIGINS` contains `*`, do not set `Access-Control-Allow-Credentials`. Better: reject `*` at boot if `ENVIRONMENT=production`. Default to `[]` (no origins) and require explicit configuration.

### 1.20 No HSTS or CSP headers  *(Medium)*

`internal/api/middleware/middleware.go:244-253` (`SecurityHeaders`) sets `X-Content-Type-Options`, `X-Frame-Options`, `X-XSS-Protection`, `Referrer-Policy`, `Cache-Control`. Missing: `Strict-Transport-Security` (HSTS), `Content-Security-Policy`, `Permissions-Policy`. `X-XSS-Protection` is deprecated and should be omitted.

**Fix:** add `Strict-Transport-Security: max-age=31536000; includeSubDomains` when `ENVIRONMENT=production`. Drop `X-XSS-Protection`. Add a basic `Content-Security-Policy: default-src 'none'` for the JSON API surface.

### 1.21 SQL injection — clean, but listing endpoints accept untrusted `sort_by`  *(Medium)*

I reviewed every `*Repository`. All raw queries use parameterized `$N` placeholders for values — no string concatenation of input. **Except** `sort_by` and `sort_order`:

- `internal/repository/postgres/user_repository.go:202-212` — `sortBy` and `sortOrder` are interpolated via `fmt.Sprintf` straight from the filter struct.
- `internal/repository/postgres/organization_repository.go:185-193` — same.
- `internal/repository/postgres/role_repository.go:214-220` — same.
- `internal/repository/postgres/organization_repository.go:328-334` — same for `ListMembers`.

The handlers (`user_handler.go:79`) accept `sort_by` and `sort_order` directly from the query string with no whitelist. So `GET /admin/users?sort_by=created_at;DROP TABLE users--` is fed unescaped into the SQL string.

This requires a `system_admin` JWT to reach, which makes it a privilege-escalation vector rather than an unauthenticated SQL injection — but a stolen system-admin token becomes a one-shot DB takeover.

**Fix:** validate `sort_by` against an allowlist per repository (`{"created_at", "updated_at", "email", ...}`). Validate `sort_order` ∈ `{ASC, DESC}` (case-insensitive). Reject anything else.

### 1.22 `Logout` swallows errors silently  *(Low)*

`internal/api/handlers/auth_handler.go:146-148` discards the `Logout` error with a comment "Log but don't fail" — but doesn't log. The user gets `success: true` even if the refresh token was invalid or the database was down. That's intentional from a UX angle but should at minimum be logged.

**Fix:** log the error with the request ID. Return 200 either way.

### 1.23 Logout endpoint is not authenticated  *(Medium)*

`routes.go:83`: `POST /auth/logout` is a **public** route. It accepts the refresh token in the body, validates it, and revokes it. Good — but combined with 1.22 (silent failure), an attacker who steals someone's *expired* refresh token can still trigger a database write per request (the UPDATE attempts and silently no-ops on `revoked = false` mismatch, but it's a query). Add basic input validation (token format) before the DB lookup.

More importantly, an attacker who steals a user's refresh token through CSRF can log them out at will. There is no CSRF protection on this endpoint (no token, no Origin check beyond CORS).

**Fix:** require `Authorization: Bearer <access_token>` AND a refresh token in the body. Reject if the access token's `user_id` doesn't match the refresh token's `user_id`.

### 1.24 SSO callback can be replayed if the user retries with the same code  *(Medium)*

State is one-shot, but the OAuth `code` is the provider's responsibility. Google rejects replays after first exchange, but a custom OAuth provider may not. Furthermore, the in-memory state TTL is 10 minutes (`manager.go:220`), longer than the typical OAuth code lifetime — leaving a window where state is reusable if the manager's atomic-delete is broken (see 1.14).

**Fix:** addressed by 1.14. Additionally, store a hash of the consumed `code+state` for an extra minute as defense-in-depth.

### 1.25 Logging hygiene  *(Low)*

I grepped for log statements that might leak sensitive data. Findings:
- `internal/api/middleware/middleware.go:105` logs `Method URL.Path StatusCode Duration` — no token in path? Yes, sometimes: `/auth/verify-email?token=...` and `/auth/sso/callback?code=...&state=...`. **The logger logs the full URL path including query string.**
- No password or refresh-token leaks found.

**Fix:** strip query strings from the access log when path matches `/auth/verify-email`, `/auth/sso/callback`. Or use structured logging with the path-only field.

### 1.26 Panic recovery is wired and handles the common case  *(No issue)*

`middleware.go:66-76` recovers from panics, logs the stack, and returns 500. Good.

### 1.27 Open redirects  *(Captured by 1.13)*

The only redirect-target surface is the SSO redirect URL. See 1.13.

### 1.28 No constant-time comparison for password reset / verify token hashes  *(Low)*

`token_repository.go:200, 261` look up by `token_hash` (SHA-256 hex). DB comparison is fast and not timing-vulnerable in practice (Postgres B-tree indexed equality), but the hash itself is computed in `service.go:485-488`. The hash is fine — SHA-256 is the right choice.

`internal/auth/jwt/service.go:485` (`hashToken`) stores SHA-256 hex. Note: SHA-256 of an unsalted 64-char URL-safe random is fine because the input has 384 bits of entropy. No issue.

## 2. Multi-tenant correctness

### 2.1 Org scope enforcement table  *(Reference)*

| Endpoint | Accepts org_id | Verifies actor∈org | Enforces role within org | Notes |
|---|---|---|---|---|
| `POST /auth/login` | optional in body | yes (`GetMembership` at `auth_service.go:340`) | reads org-scoped roles | correct |
| `POST /auth/refresh` | optional in body | partial (`auth_service.go:604`) | yes via `GetMemberRoles` | see 2.2 |
| `POST /auth/logout/all` | n/a | n/a | system-admin can reach via `revoke-sessions`; OK | correct |
| `GET /admin/*` (everything) | n/a | bypassed by `system_admin` requirement | yes | gated correctly |
| Org-context handlers (none today) | — | — | — | **none exist** — see 2.4 |

### 2.2 Refresh-token org switch silently downgrades to base roles when the user is no longer a member  *(High)*

`internal/service/auth_service.go:600-613`: when a user passes `organization_id` to `/auth/refresh`, the code:

```go
if useOrgID != nil {
    org, err = s.orgRepo.GetByID(ctx, *useOrgID)
    if err == nil && org.IsActive() {
        membership, err := s.orgRepo.GetMembership(ctx, user.ID, *useOrgID)
        if err == nil && membership.IsActive() {
            roles, _ = s.orgRepo.GetMemberRoles(ctx, membership.ID)
        }
    }
}
if len(roles) == 0 {
    roles, _ = s.userRepo.GetBaseRoles(ctx, user.ID)
}
```

If membership lookup fails, the function **silently falls back to base roles and keeps `useOrgID` set** — no, wait: `org` is only set inside the inner block, so the new token will have no org context. But the broader issue: the user **gets a successful response with downgraded roles**, no error. They think they're in org X with elevated org permissions; they're now in base context with `base_user`. Worse, an attacker who was kicked out of org X will get a refresh that quietly becomes a personal session.

**Fix:** if `useOrgID != nil` but membership lookup fails or membership is inactive, return an error (`errors.NotOrgMember()`). Don't silently downgrade.

### 2.3 Login org switch has the same shape but errors correctly  *(Reference)*

`auth_service.go:323-353` — login does return `NotOrgMember` if membership is missing. So this gap is specific to refresh.

### 2.4 No "user-of-org" endpoints exist — `/users/me/orgs`, `/orgs/{id}/me/permissions`  *(High)*

The protected user-facing API is just `/auth/me`, `/auth/sessions`, `/auth/logout/all`, `/auth/password/change`. Everything that lists or modifies org members is `/admin/*` and gated to system_admin (`requireSystemAdmin`). There is **no endpoint** for an `org_admin` to:
- list their own org's members
- invite a member
- change a member's role
- view their own org's settings

For a centralized auth server that wants org-self-service, this is a glaring hole. Today, every org operation requires a platform-system-admin token.

**Fix:** add a parallel `/orgs/{orgId}/...` namespace with `RequireOrgContext` + role/permission gates inside the org. The handlers already exist as service methods; just add the org-scoped handlers and wire them with auth that asserts `claims.OrganizationID == orgId AND claims.HasPermission("users:invite")` (or whatever).

### 2.5 `system_admin` bypass paths are not centralized  *(Medium)*

`requireSystemAdmin` is duplicated at `internal/api/handlers/user_handler.go:32`, `permission_handler.go:33`, and called from `organization_handler.go` everywhere. There's also `RequireSystemAdmin` middleware at `auth.go:182` that's never used. The "platform admin can do anything" policy is therefore implemented in handlers, not at the middleware/route layer, making it easy to forget on a new endpoint.

**Fix:** wire `authMw.RequireSystemAdmin` as the middleware on every `/admin/*` route in `routes.go` and remove the per-handler `requireSystemAdmin` calls. Then there's one place to audit.

### 2.6 Soft-delete consistency: roles read past `deleted_at` in some places  *(Medium)*

`user_repository.go:345-358` (`GetBaseRoles`) joins `roles` and filters `r.deleted_at IS NULL` — good. But `permission_repository.go:262-271` (`GetPermissions`) does not check soft-deletion of permissions and does not check that the linking `roles` row is alive. Soft-deleted permissions returning permissions to live roles is theoretically possible (currently permissions don't have a `deleted_at` column, so this is moot — but if added later, it would be wrong).

`organization_repository.go:344-349` loads user details for memberships without filtering `deleted_at IS NULL` — a soft-deleted user's name/email is still served on the members list.

**Fix:** as a discipline, every join through `users`, `organizations`, `roles` should include `deleted_at IS NULL` on the joined side. Add an integration test that soft-deletes a user and confirms they disappear from `ListMembers`.

### 2.7 Suspended-org check is missing on refresh  *(High)*

`auth_service.go:601-602` calls `GetByID` and checks `IsActive()`, but if the org is **suspended**, the function silently downgrades to base roles (per 2.2) instead of returning an explicit error. Login does this correctly (`auth_service.go:335-337`). Refresh should match.

**Fix:** if `useOrgID != nil` and `org.Status != active`, return `errors.OrgSuspended` rather than falling through.

### 2.8 No cross-tenant access tests  *(Medium)*

`tests/specs/` has no test like "user A in org X tries to fetch org Y's members and is 403'd". All admin tests run as system_admin. The cross-tenant boundary is implicit in the absence of org-scoped endpoints (2.4) and not exercised.

**Fix:** add cross-tenant tests when 2.4's endpoints land. Concretely:
- `org_admin@orgA` + `GET /orgs/{orgB_id}/members` → 403
- `member@orgA` + `POST /orgs/{orgA_id}/members` (no `users:invite` perm) → 403
- `system_admin` + same → 200

### 2.9 Refresh token's `organization_id` is stored on creation but never re-checked on refresh  *(Medium)*

`refresh_tokens.organization_id` is set when the token is minted. On refresh, we look at `claims.OrganizationID` from the JWT, not the stored row's `organization_id`. So an attacker who tampers with the JWT (impossible without the secret) could in theory pass a different org. Practical attack surface: if a user is removed from org A, their existing refresh-token row still says `organization_id=A`. The refresh path verifies membership freshly (good), but if the membership check is bypassed (per 2.2), the token effectively persists.

**Fix:** the membership re-check from 2.2 is the right defense here. Keep `organization_id` in the row for audit but don't trust it.

## 3. RBAC / permissions

### 3.1 Permissions snapshot in the JWT — known design choice with a hidden cost  *(Medium)*

Permissions are baked into access tokens at issuance (`auth_service.go:362-379`) and read from the JWT in `claims.HasPermission`. This is fast (no DB hit) but **stale**: if an admin revokes a permission from a role, every outstanding access token for users who have that role still holds the perm until natural expiry (≤15 minutes). For high-privilege ops (user deletion, financial), this 15-minute window is meaningful.

The `revoke_sessions: true` flag on `SetUserRoles` (`user_handler.go:222-279`) addresses this for *role* changes by logging the user out — but that flag defaults to `false`, doesn't apply when *permissions* of a role are changed, and doesn't apply when an *organization* changes its own role mappings (when that lands).

**Fix:**
1. Per-user "token version" in Redis (mentioned in 1.10). On role/permission change, bump the version. JWT carries `tv` claim; downstream services compare. Cheaper than blacklisting.
2. Document that a 15-minute lag is the security guarantee. Anyone who needs immediate revocation must call `revoke_sessions`.

### 3.2 Privilege escalation: there is no role-hierarchy check in `SetUserRoles` or `AddMember`  *(High)*

`user_handler.go:197-298` (`SetUserRoles`) lets a system_admin assign any base role, including `system_admin` itself. That's fine for system_admin since they already have everything. But:

- `organization_handler.go:263-317` (`AddMember`) is also gated to system_admin only — fine for now.
- **When org-scoped admin endpoints land (per 2.4)**, an `org_admin` will need to assign roles. If the implementation copies `AddMember`'s shape, an `org_admin` could assign `org_admin` to a coworker (escalation within org — arguably OK) **or could assign `system_admin` if it accidentally accepts a non-org role** (catastrophic). The current `AddMember` does not validate that the role is org-scoped or that it's at-or-below the caller's level.

`organization_service.go:361-383` (`AssignMemberRole`) does check `role.IsOrgRole`, which is the right shape. Make sure the future org-admin handlers go through that path, not the raw repo.

**Fix:** define `role.level` semantics (already a column at `roles.level` per `001_initial_schema.up.sql:137`). On role assignment, reject if the requested role's level < the caller's lowest role level. Document clearly. Add tests.

### 3.3 Custom per-org roles — not implemented (known gap)  *(Roadmap)*

CLAUDE.md notes this. Sketch:
- `roles` table already has `organization_id` and `is_org_role` columns — no schema change needed for the basic shape.
- Add `POST /orgs/{orgId}/roles` (create custom role), `PUT /orgs/{orgId}/roles/{roleId}/permissions` (set perms).
- Permission allowlist: an org cannot grant a permission its `system_admin` hasn't approved at the platform level. Add a `permissions.org_assignable BOOLEAN` column to flag which permissions can be embedded into custom roles.
- Service-self-registered permissions (per migration 005) should default `org_assignable=false` and require explicit opt-in.

### 3.4 Permission cache invalidation has no story  *(Medium)*

When a user's role changes:
- New tokens issued after the change carry the new permissions.
- Outstanding tokens carry the old permissions until expiry.
- The `tokenCache` (per 1.11) holds parsed claims keyed by token hash with TTL = remaining lifetime. **No invalidation on permission change.**

The handlers force-revoke via `revoke_sessions: true` (line 278 of `user_handler.go`), which calls `LogoutAll` — but `LogoutAll` only revokes refresh tokens (per 1.10). Access tokens stay valid.

**Fix:** combine 1.10 (token-version counter) with 3.1. The version bump is the single point of truth; it invalidates the cache, the refresh tokens, and signals downstream services to reject by checking the version claim.

## 5. Error handling + resilience

### 5.1 No graceful shutdown of in-flight requests' DB / Redis work  *(Medium)*

`cmd/server/main.go:144-156` calls `server.Shutdown(ctx)` which drains HTTP connections (good), then `defer db.Close()` and `defer redisClient.Close()` close those after `main` returns. But the DB pool's open transactions can be cancelled mid-flight when `Close` is called. There's no explicit context propagation from the shutdown signal to long-running handlers.

**Fix:** add a request-context-aware ShutdownContext that handlers can check. Wait for `server.Shutdown` to complete *before* closing DB/Redis. Today the order is: signal → server.Shutdown (waits) → main returns → defer closes run. So actually this is correct in shape. **No issue, on second look.**

### 5.2 Postgres outage at boot kills the process  *(Medium)*

`postgres/db.go:36` does `PingContext` with a 5s timeout; failure → `log.Fatalf`. For a multi-replica deployment behind a slow startup, each replica retries via the orchestrator's restart policy. Fine but slow.

**Fix:** retry the initial ping with exponential backoff for ~30s before giving up. Useful when DB starts simultaneously with auth.

### 5.3 Migration failure handling  *(Low)*

Migrations run in `scripts/entrypoint.sh` per CLAUDE.md, not in Go. If the migration script fails, the entrypoint aborts before launching the binary. Good — fail-fast on schema mismatch. **No issue.**

### 5.4 Email send failure semantics — registration succeeds without email  *(Medium)*

`auth_service.go:243-252`: registration tries to send the verification email. If it fails, the user is still created and the response returns `verification_email_sent: false`. The user is in `pending` state, locked out of full functionality, with no way to retry email send.

**Fix:** add `POST /auth/verify-email/resend` (rate-limited, requires unauthenticated email input). Make registration's email failure log loudly with the request ID.

### 5.5 Context propagation through handlers → services → repos  *(No issue)*

Every service method takes `ctx context.Context` as the first arg. Repos use `getQuerier(ctx, db)` which propagates the transaction context. `ExecContext` / `GetContext` honor cancellation. **OK.**

### 5.6 Long-running goroutines without shutdown signal  *(Medium)*

Two goroutines run for the server's lifetime without a stop channel:
- `internal/auth/sso/manager.go:90` — state-store cleanup, every 5 min.
- `internal/api/middleware/middleware.go:194` — rate-limiter cleanup, every 5 min.

On `server.Shutdown`, these keep running until the process exits. They don't hold critical resources, but they're orphaned.

**Fix:** pass a `context.Context` to these constructors so they exit cleanly.

### 5.7 Email service nil-check pattern is inconsistent  *(Low)*

Some places (`auth_service.go:244`) check `s.emailService != nil` before calling. Others assume non-nil. The constructor in `main.go:64-74` always sets at least a NoOpEmailService, so it's never nil — but the defensive checks add noise.

## 8. API surface for centralized auth use case

### 8.1 Registration flexibility — three modes  *(High)*

Today the only mode is "register-or-error." Three useful additions:

- **`mode: "login-or-register"`** — try login with given credentials, register if user doesn't exist. Idempotent for client UX. Risk: timing-side-channel for user-existence (see 8.2). Mitigation: always run the bcrypt comparison even on register-path so the response time is similar.
- **`mode: "register-or-error"`** — current behavior.
- **`mode: "register-or-return"`** — return the existing user object if email is taken, without attempting login. Use case: idempotent provisioning by service-to-service (consumer app calls auth-server during user signup, doesn't care if user existed or not). **Must require service-to-service auth — never expose to public clients** because it leaks user-existence.

**Fix:** add `RegisterRequest.Mode string` accepting `register|login_or_register|register_or_return`. Default `register`. Gate `register_or_return` behind a service-auth check. Cover with tests.

### 8.2 User-existence check  *(Medium)*

Useful for client UX ("That email is already registered — log in instead?"). Today this is impossible without trying to register and parsing the 409 response, which leaks the same info but is awkward.

Tradeoffs:
- Without a check: clients have to do `register or login` flow heuristically.
- With a check: trivial to enumerate the user pool. Even captcha-protected, attackers can run distributed checks.

**Recommendation:** add `POST /auth/check-email { email }` returning `{ exists: bool }` only when the request includes a service-to-service auth header (M2M token). Do **not** expose to public clients. For public clients, return a generic message from registration ("email already registered or invalid") — never confirm existence.

### 8.3 App scopes — the central design question  *(High — design decision)*

The user wants multiple consuming apps (release-manager, auction, future products) to share one user pool. Two architectures:

**A. Shared pool, no app concept** — every user is implicitly a user of every app. Authorization is purely role/permission-based, with services declaring their permission slices (which migration 005 already supports). JWT carries no `app_id`.

**B. Shared pool with app association** — `apps` table + `user_apps` junction. JWT carries `app_id`. Permissions can be app-scoped. Apps have isolated permission catalogs. A user's first login to app B requires a (possibly auto-approved) "claim" of that app.

**Recommendation: go with B**, because:
- It gives operators a clear "user X has access to release-manager but not auction" dial.
- It's how every other multi-app SSO (Auth0, Cognito, Keycloak, Okta) does it.
- Migration 005 already has `permissions.service`. Extending to `apps` is a small additional layer.
- Without it, every consumer app must implement its own "is this user allowed here?" check using base roles or org membership, which is brittle.

**Schema sketch:**

```sql
CREATE TABLE apps (
    id UUID PRIMARY KEY,
    code VARCHAR(100) NOT NULL UNIQUE,        -- 'release-manager', 'auction'
    name VARCHAR(200) NOT NULL,
    description TEXT,
    allowed_redirect_urls TEXT[] NOT NULL,    -- for OAuth flows from this app
    permission_service VARCHAR(100),          -- which 'service' in permissions table this app owns
    auto_grant_on_signup BOOLEAN DEFAULT false,
    status VARCHAR(20) DEFAULT 'active',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE user_apps (
    user_id UUID NOT NULL REFERENCES users(id),
    app_id UUID NOT NULL REFERENCES apps(id),
    granted_at TIMESTAMPTZ DEFAULT NOW(),
    granted_by UUID REFERENCES users(id),
    status VARCHAR(20) DEFAULT 'active',  -- 'active', 'revoked'
    PRIMARY KEY (user_id, app_id)
);
```

JWT changes: add `app_id` and (optionally) `app_code` claims. Refresh tokens scoped to (user_id, app_id, organization_id).

**Recommendation: scope refresh tokens to (user, app, org)**. Rationale: if release-manager has a 7-day refresh and auction has a 30-day refresh, today the longest wins because refresh tokens are user-scoped. With app scoping, each app's policy is honored. ## 9. Frontend client SDK preparation

### 9.1 Refresh-rotation race when N tabs share storage  *(High — design)*

The Preact client at `../../auction/client/` (and the future browser SDK) will store the refresh token somewhere (cookie, localStorage). If the user has 5 tabs open and each one independently decides to refresh because its access token is stale, all 5 fire `POST /auth/refresh` simultaneously — the first wins, the next 4 see "token revoked" (because rotation revokes the presented token).

Three patterns to choose from:
- **Web Locks API** (`navigator.locks.request`): single tab does the refresh, others await. Modern browsers, but requires same-origin SDK.
- **BroadcastChannel** + leader election: similar shape, broader support.
- **Server-side leeway**: the refresh handler treats a token presented within ~5s of its rotation as "still valid," returning the most recent issued pair. This is the OAuth2 "refresh token rotation grace period" pattern. Server-side, easier to roll out.

**Recommendation:** server-side leeway + client-side BroadcastChannel mutex. On refresh, if the presented token is `revoked=true && revoked_at < now - 5s`, look up the family head's most recent token and return that. Combine with the family-revocation rule from 1.9.

### 9.2 Cookie vs Authorization header for browser  *(High — design)*

Today the bearer header is the only first-class path; cookies are accepted but never set by the server. For a browser SDK, **HttpOnly + SameSite=Lax + Secure cookies** are safer (immune to XSS-driven token theft) but require:
- Server-side cookie-set on `/auth/login`, `/auth/refresh`, `/auth/sso/callback`.
- CSRF protection (double-submit cookie or Origin check) on every state-changing endpoint.
- CORS configuration that *names* the specific origins (no `*`, see 1.19), with `credentials: include`.

Worth doing for first-party browser apps. Mobile / native / server-to-server consumers continue to use bearer.

**Fix:** add `cookie_mode` flag on `/auth/login` request: when true, response sets cookies and *omits* tokens from the body.

### 9.3 PKCE for public clients  *(High — design)*

When a browser app initiates OAuth directly (not server-side handoff), the client_secret cannot be stored client-side. The OAuth flow therefore must use PKCE (RFC 7636). Today, `auth_service.go:421+` exchanges the code with the configured `client_secret` server-side, so the auth-server is acting as a confidential client — but the redirect URL is whatever the browser passes (per 1.13), so the boundary is muddled.

**Recommendation:** for browser-initiated flows, accept `code_verifier` on the callback and pass `code_challenge` to the provider on `GetSSOAuthURL`. Validate provider PKCE support per provider (Google supports it, GitHub does not as of last check).

### 9.4 Idempotency keys on flaky-network registration / login  *(Medium)*

Mobile clients on bad networks retry POSTs. Without idempotency, double-clicks during registration create two users; double-login creates two refresh-token rows.

**Fix:** accept `Idempotency-Key` header on `/auth/register`, `/auth/login`. Store key+user-id+result in Redis for 5 minutes. On replay, return the cached result. Standard pattern.

### 9.5 WebSocket auth path (future)  *(Low — design)*

When the auction client adds WebSocket bidding, the server-side WS handshake must auth. Two paths: (a) `Sec-WebSocket-Protocol: Bearer, <token>` header; (b) initial frame contains the token. Recommend (a) because it works in the handshake. Renewal: client closes and reconnects with a fresh access token — no in-flight token swap.

### 9.6 CORS allow-headers list is incomplete  *(Low)*

`middleware.go:49` allows `Accept, Authorization, Content-Type, X-Request-ID`. For the SDK we need to add `Idempotency-Key`, `X-CSRF-Token` (when 9.2 lands).

### 12.3 Auditor's verdict

Where the audit started: **1 Critical, 25 High, 27 Medium, 5 Low** — a
codebase that worked but had real, exploitable bugs (reusable
single-use tokens, silent BcryptCost downgrade, no refresh-token theft
detection, CORS `*`+credentials, etc.) and lacked the multi-tenant /
multi-app surface the user was asking for.

Where it landed: **all Critical / High closed**, **24 / 27 Medium
closed** (the remaining three are deferred-by-design or
platform-layer concerns documented above), **4 / 5 Low closed** (the
remaining one is a deliberate "defer until a consumer asks").
Centralised-auth design questions from §8 — registration modes,
user-existence check, app scopes, app-scoped permissions, JWT app
claims, refresh scoping — are all live in the code, not just on the
roadmap. The frontend SDK foundation (`@rw3iss/auth-client`,
hexagonal, framework-agnostic, drop-in for the future marketplace
SDK) is also live.

**Production-readiness assessment:** the server now meets the bar the
audit was written to define. Remaining open items are improvements,
not blockers. Suitable to begin consumer onboarding (release-manager
is the obvious first integration via `@rw3iss/auth-server-client`).
